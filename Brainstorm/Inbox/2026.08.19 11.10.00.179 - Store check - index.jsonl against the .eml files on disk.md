# Store check: index.jsonl against the .eml files on disk

Kategori: storage-integrity | Efor: M | Rank: 1

## Ne
A read-only `StoreCheckService` under `MainProject/Services/Mail/` that walks `AppPaths.UserCache/Accounts/*/Folders/*` with plain file I/O — deliberately NOT through `MessageStore.GetFolders`/`GetIndex`, which skip and collapse the very defects being hunted — and classifies five findings, each carrying the exact path: (1) invisible folder — a directory holding `index.jsonl` or `Messages` with no `folder.json`, or one that fails to deserialize into `MailFolderData`; (2) orphan body — a `Messages/<uid>.eml` whose uid has no line in `index.jsonl`; (3) empty body — a zero-byte `.eml`; (4) stray temp — a leftover `index.jsonl.tmp` or `<uid>.eml.tmp` from `AtomicFile.WriteAllText`/`WriteAllBytes`; (5) badge drift — `folder.json` `UnreadCount` disagreeing with the rows, reported only when `rows >= TotalCount`, the same gate `RefreshUnreadCount` uses (MessageStore.cs:229) to decide the cache holds the whole folder. Drop the proposed sixth class, duplicate uid lines: `SaveIndex` (MessageStore.cs:287) rewrites the file from a `ConcurrentDictionary`, so the app can never produce one. Report shape mirrors `TrimReport`: `RanAtUtc`, a per-folder dictionary keyed "<email> / <folder>", byte totals, persisted to `UserData/store-check.json` through `AtomicFile`, with a `LastReport` property read from disk on first access exactly like `OfflineCacheTrimmer.LastReport`. Surfaced by `case ("GET", "/store/check")` in `DebugApi` (fresh scan) and one row in Settings.razor's `🧰 Diagnostics` `GlassCard` (line 230) showing the last scan's counts. Read-only by construction, like `RuleEngine.Preview` behind `/rule-preview`. Verified by planting damage with file operations — rename a `folder.json`, copy an `.eml` onto an unused uid, truncate one to zero bytes, drop an `index.jsonl.tmp` — then calling `/store/check` and reading the counts back; no screen interaction.

## Neden
A folder directory that lost or never got its `folder.json` is invisible to everything: `GetFolders` line 81 is `if (!File.Exists(infoPath)) continue;`, so the folder list, `SearchService` and `OfflineCacheTrimmer.MeasureCachedBodies` (line 124, which iterates `GetFolders`) all walk past it while its `.eml` files keep occupying disk and count against no cache budget. Note the reachability is narrower than first claimed: IMAP writes `folder.json` for every folder in `SyncFolderListAsync` (ImapSyncService.cs:246) before any message sync, so an interrupted IMAP first fill does NOT produce this. POP3 does — `SummaryPump.DrainToStoreAsync` upserts at line 33 and `Pop3Service` writes the folder info only afterward at line 73 — and so does a `folder.json` that is deleted or fails to deserialize, which `GetFolders` swallows into a warning log nobody reads. Orphaned bodies are equally invisible: `RemoveMessages` line 274 logs and continues when a `File.Delete` throws, and `MoveToLocalFolder` writes the body (line 366) before `UpsertSummaries` (line 368), so a crash in between strands it. Stray `.tmp` siblings are never read or swept by any code in the tree — grep for `.tmp` hits only `AtomicFile.cs` itself. Today the single symptom of all of this is a cache larger than the app believes it is, with no way to ask why. Take the check alone and leave repair out: a delete-capable pass built on a classifier that has never run once is the wrong order, and the proposed repair bundles three separate features (a `FromSafeName` decoder, MIME re-adoption through `MimeMessage.Load`, and `folder.json` reconstruction) under one title.
