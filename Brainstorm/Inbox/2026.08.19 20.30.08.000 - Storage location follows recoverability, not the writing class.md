# Storage location follows recoverability, not the writing class

Kategori: data-integrity | Efor: M | Rank: 1

## Ne
MessageStore has ONE path builder and it is hardcoded to the cache root:

    static string AccountCacheFolder(string accountId) =>
        Path.Combine(AppPaths.UserCache, AccountsFolderName, accountId);

No IsLocal branch, no branch for app-local fields. So everything routed through
MessageStore inherits UserCache, including two kinds of data that can never be
re-downloaded:

1. Local folders. ComposeService.StoreInLocalFolder writes Local/Drafts,
   Local/Outbox and Local/Sent with the same SaveFullMessage + UpsertSummaries
   calls the IMAP sync uses, so drafts and queued outgoing mail live in a folder
   named "cache" with no server copy behind them.
2. App-local summary fields, which ride along inside index.jsonl:
   MailMessageSummary.Tags, MailFlags.Important (64), MailFlags.Muted (128) and
   SnoozedUntilUtc. None of these exists on any server.

Split the location by recoverability instead of by writer: server bodies stay in
UserCache; local folders and the app-local fields move under UserData, with a
one-time migration that adopts what is already sitting in UserCache. Then fix
the class summary, which currently states the false invariant as fact:
"Deleting UserCache is always safe: everything here re-syncs from the server."

## Neden
That sentence was true while MessageStore held only synced IMAP/POP3 mail. It
stopped being true twice -- when the app-local fields were added to the summary,
and when local folders were introduced -- and was never revisited. Nothing in
the code enforces it, so nothing failed when it became false.

It has already produced one real bug: OfflineCacheTrimmer trusted the same
sentence and had local folders in its deletion pool, so a draft would reopen
empty and an Outbox message the user had already pressed Send on would be
deleted outright by the next flush. That was fixed by teaching the TRIMMER to
check IsLocal -- the symptom, not the cause. The store still puts irreplaceable
data behind a name that promises the opposite, so the next consumer that trusts
the name walks into it again. Any "clear the cache" affordance, in the app or by
hand in Explorer, is the obvious next one.
