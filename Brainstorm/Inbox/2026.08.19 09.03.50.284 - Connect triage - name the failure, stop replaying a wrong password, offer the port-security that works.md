# Connect triage: name the failure, stop replaying a wrong password, offer the port/security that works

Kategori: onboarding-reliability | Efor: M | Rank: 1

## Ne
New `MainProject/Services/Mail/ConnectTriageService.cs` returning `ConnectDiagnosis(DiagnosisKind Kind, string Sentence, string Stage, int? SuggestedPort, ConnectionSecurity? SuggestedSecurity)`. Three pieces, in this order:

(1) Stop retrying credential rejections. `ResiliencePolicy.cs:30` currently reads `ShouldHandle = new PredicateBuilder().Handle<Exception>(static ex => ex is not OperationCanceledException)` with `MaxRetryAttempts = 3`, so one Test click with a wrong password sends four logins. Narrow the predicate to exclude `MailKit.Security.AuthenticationException` and `ServiceNotAuthenticatedException`, keeping retries for `SocketException`/`IOException`/timeout. Narrow it in the shared pipeline, not just the wizard path: a wrong stored password otherwise fires four logins on every scheduled sync pass too.

(2) Classify what broke and where. `MailConnections.OpenAsync` (MailConnections.cs:42-58) is one shared body for IMAP/POP3/SMTP and records no stage, so the wizard's `TestMessage = $"❌ {ex.Message}"` (AccountWizard.razor.cs:134) looks identical whether the incoming or the sending server refused. Have `TestConnectionAsync` call the triage service per stage and map DNS failure (`SocketError.HostNotFound`) vs refused socket (`ConnectionRefused`) vs `SslHandshakeException` vs auth rejection vs timeout to a plain sentence naming the stage.

(3) On socket/TLS failures only, probe the small matrix for that same host — IMAP {993 SslOnConnect, 143 StartTls, 143 None}, POP3 {995 SslOnConnect, 110 StartTls}, SMTP {465 SslOnConnect, 587 StartTls, 25 StartTls} — connect-only, never AUTH, one short timeout, and report the pair that answered. The wizard renders the sentence plus a `CoreChip` that writes the winner into the live `IncomingPortText`/`IncomingSecurity` or `SmtpPortText`/`SmtpSecurity` fields. Skip the probe entirely for auth rejections — the settings are already right there.

Add `GET /connect-diagnose?host=&port=&security=&protocol=&stage=` to `zTests/DebugApi.cs` (it has no connect-test route today) returning the same record as JSON; verifiable against a local listener that refuses, hangs, or rejects AUTH.

## Neden
Verified in the repo: the wizard prints raw MailKit text, does not say which server refused, and there is no way to fix a bad setting afterwards — `AccountSettingsPage.razor` exposes only display name, color, enabled and per-account settings, with no host/port/security field, so a wrong port means deleting the account and re-running the wizard. Meanwhile the retry predicate retries everything, turning a mistyped password into four failed logins against Gmail/Yahoo per click, which is how a provider starts rate-limiting. `ProviderPresets.Custom` is a blank host with a guessed 993/995/465 SslOnConnect, so every self-hosted or corporate server lands there, and the port/security pairing is exactly the thing a preset cannot know. No exception classification exists anywhere in the codebase today (the only near-miss is `ComposeService.cs:311` for outbox retry).
