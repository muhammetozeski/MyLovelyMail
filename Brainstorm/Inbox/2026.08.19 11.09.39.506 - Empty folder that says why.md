# Empty folder that says why

Kategori: diagnostics | Efor: S | Rank: 2

## Ne
Replace the dead-end string at Mail.razor:191 with a panel that names the reason and offers the action that fixes it.

Today the list's else branch (Mail.razor:189-199) prints "This folder is empty" for every case the two branches above it did not catch. That same sentence appears when the fetch failed, when the account is paused, when the folder was never synced, and when the server says 400 messages and the cache holds none.

First, a prerequisite the original idea missed: KickFolderSync's catch (ImapSyncService.cs:59-62) only calls Log(...). MarkFailure is reached only from SyncScheduler.cs:100 and ImapIdleService.cs:129/135, so a failed folder-on-open sync sets no account health, draws no rail badge, and lands the user on the dove with no trace anywhere but the Logs page. Record the error per folder in that catch (a static dictionary keyed by MessageStore.FolderKey holding message + UTC is enough; no new file under AppPaths.UserData) and clear it on the next success.

New MainProject/Services/Mail/FolderEmptyReason.cs: a pure Explain(MailFolderData folder) reading only cached state, returning a headline, a detail line, and an optional action. Branches in order, each backed by a field verified to exist:
- AccountStore.GetById(folder.AccountId) is { Enabled: false } -> "This account is paused" (SyncScheduler.cs:83 skips it), action re-enables it.
- the new per-folder error, or SyncHealthService.For(accountId).IsFailing -> "Last fetch failed" plus the message and time, action opens ConnectTriageService.
- folder.LastSyncedUtc == null -> "Never fetched yet", action calls ImapSyncService.KickFolderSync.
- folder.TotalCount > 0 while MessageStore.GetSummaries(...).Count == 0 -> "The server has N messages here, none are cached". The action must be KickFolderResync, NOT KickFolderBackfill: BackfillFolderAsync returns 0 at ImapSyncService.cs:118 when OldestFetchedUid is not > 1, so a backfill on an empty cache does nothing. The "Showing X of Y" footer and its Load-older button (Mail.razor:348-364, TruncatedFolder at Mail.razor.cs:240) live inside the non-empty branch and are unreachable here anyway.
- POP3 account on a non-Inbox folder -> "POP3 only ever fills the Inbox" (MailUiState.cs:113-115 kicks nothing for it).
- everything else -> the current wording plus "server count 0, checked at HH:mm" from TotalCount and LastSyncedUtc, so an honestly empty folder proves it.

DebugApi: GET /folder-why?account=..&folder=.. returning the chosen reason and action, next to the existing routes in RouteAsync.

Verify without touching the screen: POST /accounts/enabled for the paused branch; POST /resync then an immediate GET /folder-why for the never-fetched and cache-empty branches while the fetch is in flight; point an account at a dead port and open a folder to reach the failed branch; GET /dom to confirm the panel and its button render.

## Neden
A folder with nothing in it is the one empty state a mail client cannot be vague about, because the user cannot tell "there is no mail" from "the app failed to fetch it". The failure path is genuinely silent: KickFolderSync swallows its exception into a log line, SyncHealthService is untouched, so no rail badge fires and the screen says "empty". Every other fact needed is already sitting in MailFolderData (TotalCount, LastSyncedUtc, OldestFetchedUid) and AccountStore; the screen simply never consults them. Accepted over the sync ledger because it is smaller, fixes a wrong statement rather than adding a second place to look, and the ledger overlaps the shipped Logs page and per-account SyncHealthService.
