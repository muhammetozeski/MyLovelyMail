# Cache budget for OfflineCacheTrimmer, with a dry run and a receipt

Kategori: cache-pruning | Efor: S | Rank: 2

## Ne
Add Settings.OfflineMaxCacheMb = new(0) directly under OfflineKeepDays (Settings.cs:63) and the matching InheritedSetting<int> in AccountSettings.cs beside line 26 — AccountSettingsPage.razor's @foreach over AccountSettingsOf.GetAllSettings() (line 64) renders the per-account override row as a number input with zero UI work (the global Settings.razor hand-writes its rows and gets none, exactly like OfflineKeepDays today). Change OfflineCacheTrimmer.TrimAll() from void to TrimAll(bool dryRun = false) returning a TrimReport(DateTime RanAtUtc, long BytesFreed, int BodiesDropped, Dictionary<string,long> ByFolder, bool WasDryRun). Keep the existing age pass as the first stage, then add a size stage: when an account's cached body bytes exceed the budget, drop bodies oldest-first by summary.DateUtc (the field the age pass already keys on at line 27) until it fits. Sizes come from new FileInfo(MessageStore.MessagePath(...)).Length, skipping summaries whose body is not on disk — MessagePath is already public (MessageStore.cs:47), so MessageStore needs no change and deletion still goes through the existing MessageStore.DeleteCachedBody, keeping summaries intact so rows survive and bodies re-download on open. A dry run walks and measures identically but deletes nothing. Persist the last report to UserData/cache-trim.json using the exact SyncHealthService pattern (AtomicFile.WriteAllText + JsonDefaults.Indented, load-on-first-access static). SyncScheduler.cs:113 keeps calling it, now logging the returned report unconditionally instead of the current conditional one-liner. Verify with a new DebugApi POST /trim?dry=true (report only, nothing deleted), then POST /trim, reading GET /logs?filter=trim and the persisted receipt between calls.

## Neden
TrimAll returns void and logs only inside `if (removed > 0)`, while `if (keepDays <= 0) continue;` at line 19 exits with no trace at all — so a trimmer that found nothing, a trimmer disabled by the default of 0, and a trimmer that never ran all produce byte-identical output. There is no way to tell which happened. It also only understands age, which is the wrong axis for the actual complaint: one folder of large attachments blows past any budget while a year of plain text costs nothing. A dry run lets the app say 'would free 240 MB' before anything is destroyed, and the persisted receipt turns the current silence into 'last trim 18 Aug 09:14 — freed 240 MB, 1,204 bodies'.
