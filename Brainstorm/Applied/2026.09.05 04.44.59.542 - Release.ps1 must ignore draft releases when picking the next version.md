# Release.ps1 must ignore draft releases when picking the next version

Kategori: resilience | Efor: S | Rank: 1

## Ne
In `Release.ps1`, the next version is computed from
`gh release list --limit 100 --json tagName --jq '.[].tagName'`, which includes DRAFT releases.
A draft release has no git tag, so the script then runs `git log "$lastTag..HEAD"` against a ref
that exists neither locally nor on the remote; git fails with "fatal: ambiguous argument",
`$subjects` comes back empty, and the script dies with the misleading message
"No commits since <tag> - nothing to release."

This actually happened: a v1.37.0 draft left behind by an interrupted run on 2026-09-03
(0 assets, never published) blocked every subsequent release until it was deleted by hand.

Fix: filter drafts out when picking the highest tag - add `isDraft` to the `--json` field list and
drop entries where it is true (e.g. `--jq '.[] | select(.isDraft | not) | .tagName'`). Separately,
make the failure honest: if `git log "$lastTag..HEAD"` cannot resolve the range, say that the tag
does not exist locally rather than reporting "nothing to release". Check whether a
`git fetch --tags` is enough to resolve it first.

Verify with `.\Release.ps1 -Bump minor -WhatIf` after creating a throwaway draft release, then
delete the throwaway draft.

## Neden
A leftover draft silently blocks every future release, and the error message points at the wrong
thing ("nothing to release" when there are seventeen commits waiting). The release script is the
last step of every loop turn, so a trap there stops shipping entirely.
