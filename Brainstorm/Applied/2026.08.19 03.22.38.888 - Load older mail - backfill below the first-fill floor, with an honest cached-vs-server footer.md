# Load older mail: backfill below the first-fill floor, with an honest cached-vs-server footer

Kategori: sync-completeness | Efor: M | Rank: 1

## Ne
Add `OldestFetchedUid` to `MailFolderData`, set alongside `LastSeenUid` in `SyncOpenedFolderAsync`, backfilled once as `min(uid)` of the cached index when 0. IMPORTANT — `SaveFolder` is called from TWO sites: `SyncOpenedFolderAsync` (~line 270) and `SyncFolderListAsync` (~line 151). The second rebuilds `MailFolderData` from scratch on every folder-list refresh and already carries `LastSeenUid` across by hand because of a past bug documented in the comment there (dropping it to 0 're-imported the newest 300 as brand-new on EVERY pass'). Carry `OldestFetchedUid` through BOTH sites or it gets wiped on the next refresh and the backfill silently re-runs forever.

Add `ImapSyncService.KickFolderBackfill(account, folderFullName, count)` reusing the existing `onDemandInFlight` set + `OnFolderSyncStateChanged` event, following the `SyncFolderAsync` connection pattern (`ResiliencePolicy.RunNetwork` + `MailConnections.OpenImapAsync` + `SyncScheduler.EnterSyncScope`): open the folder read-only, `SearchAsync(SearchQuery.Uids(new UniqueIdRange(UniqueId.MinValue, new UniqueId(OldestFetchedUid - 1))))`, take the newest `count` uids, `FetchAsync(thoseUids, SummaryItems)`, `MessageStore.UpsertSummaries`, then lower `OldestFetchedUid` — never touching `LastSeenUid`, so the new-mail path and the notification condition stay untouched.

In `Mail.razor`, after the `</Virtualize>` block (line ~279), render a footer when `MailUiState.SelectedFolder is { IsLocal: false } f && FilteredSummaries.Count < f.TotalCount`: "Showing 300 of 4,821 here" plus a `⬇️ Load 300 older` button, swapped for `<CoreSpinner />` while `ImapSyncService.IsFolderSyncing(...)` is true. Hide it when `SearchAllFolders` is on.

Verify through the DebugApi: add `POST /backfill?accountId=&folder=&count=` returning how many summaries landed, extend `GET /folders` with `CachedCount` and `OldestFetchedUid`, then call `/backfill` twice and watch `GET /messages?take=1000` grow while `/folders` shows `OldestFetchedUid` falling and `LastSeenUid` unchanged. Re-run a folder-list sync between the two calls to prove the new field survives `SyncFolderListAsync`.

## Neden
Verified against the repo: `MailFolderData` has no oldest-uid field; `SyncOpenedFolderAsync` first-fills by INDEX (`startIndex = Math.Max(0, folder.Count - InitialFetchCount)`, `InitialFetchCount = 300`) then sets `LastSeenUid = maxUid`, and every later pass fetches only `new UniqueIdRange(new UniqueId(lastSeenUid + 1), UniqueId.MaxValue)`. Nothing below the floor is reachable by any code path in the app.

The hole is silent: `SearchService.cs:52` iterates `MessageStore.GetSummaries(...)`, so a mail past the 300th newest cannot be found by any search, saved search or filter — the user searches for something from last year, gets nothing, and concludes the app lost it. Meanwhile `MailFolderData.TotalCount` already holds the server's real number, so the app knows it is showing an incomplete folder and says nothing.

The only existing way out is `KickFolderResync`, whose tooltip at `Mail.razor:91` reads verbatim `title="Redownload this folder (newest 300 messages)"` — it clears the cache and re-fetches the same newest 300, and can never reach older mail. `OfflineCacheTrimmer` deletes only bodies and keeps summaries, so it will not undo a backfill. This closes the one hole in the store that no amount of re-syncing can fill, and the footer turns a silent truncation into a stated one.
