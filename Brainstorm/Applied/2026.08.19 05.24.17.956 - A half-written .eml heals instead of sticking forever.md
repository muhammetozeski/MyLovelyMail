# A half-written .eml heals instead of sticking forever

Kategori: data-integrity | Efor: S | Rank: 1

## Ne
Accepted with the scope cut down to two changes; the third (SweepInterruptedWrites) is dropped and the self-heal is moved out of TryLoadMimeMessage.

(1) Give AtomicFile a WriteAllBytes(path, bytes) twin of its WriteAllText (temp sibling, then File.Move overwrite) and have MessageStore.SaveFullMessage (Storage/MessageStore.cs:293) use it instead of plain File.WriteAllBytes. That stops new corruption at the only writer that skips the crash-safe path.

(2) Put the self-heal in MailBodyRenderer.Render's existing catch (Services/Mail/MailBodyRenderer.cs:68-72), NOT in MessageStore.TryLoadMimeMessage as originally proposed. In that catch: if folderFullName does not start with MessageStore.LocalFolderPrefix, call MessageStore.DeleteCachedBody and return null; local folders keep today's preview fallback. Returning null is exactly what the reader's refetch branch at UI/Pages/Mail.razor.Reader.cs:117 already waits for, so the heal costs no new UI and no new download code.

Why the move matters: adding the catch inside TryLoadMimeMessage would change OutboxService.cs:156-160, where a null return means RemoveMessages -- the queued outgoing message is deleted. Today the parse exception propagates to the catch at line 168 and the message stays queued for the next flush pass. Swallowing it there would turn a corrupt outbox .eml into permanent loss of the user's unsent mail. ComposeService.cs:76 (Drafts) and MessageStore.MoveToLocalFolder targets have the same no-server-copy problem. Render is the one call site where 'corrupt reports itself as a successful render' actually happens, and it is the only one that needs to change.

Dropped: SweepInterruptedWrites. Nothing in the codebase writes *.part -- AtomicFile.cs:13 is the only .tmp writer, and a leftover <target>.tmp is overwritten by the next write of that same target. It sweeps litter that does not exist.

Verification through the DebugApi, no screen clicks: GET /message to cache a real body, truncate UserCache/Accounts/<id>/Folders/INBOX/Messages/<uid>.eml to zero bytes (the residue of a killed File.WriteAllBytes), then GET /message. Note the handler at zTests/DebugApi.cs:335-360 only downloads when !HasFullMessage and does not re-render after a null, so as-is this takes two calls: the first heals (bodyHtml null, file deleted), the second refetches and returns the full body. Add the one-line re-render-after-null to /message so it matches the reader path and the check is a single call. Negative case: repeat against a folder under LocalFolderPrefix and assert the .eml is still on disk.

## Neden
MessageStore.SaveFullMessage at Storage/MessageStore.cs:293 is the only body writer that skips AtomicFile -- plain File.WriteAllBytes, which truncates before it writes. Kill the process mid-write and a zero-byte or partial .eml stays. It is called on every body fetch: ImapSyncService.cs:195 (a 50-message slice fill is 50 writes), Pop3Service.cs:195, the attachment prefetch loop, ComposeService.cs:319. This app is killed routinely -- tray Exit, the launcher restarting a duplicate instance, Windows shutdown.

What follows is silent and permanent. HasFullMessage (line 290) is File.Exists, so it returns true for the corpse and ImapSyncService.cs:246 skips it; DebugApi.cs:344 and :575 skip the download too. MailBodyRenderer.Render loads it at line 49, the parse fails, and the catch at line 71 returns a NON-null RenderedBody carrying only summary.PreviewText. Because it is non-null, the refetch branch at Mail.razor.Reader.cs:117 never fires. Either MimeKit branch lands in the same place: a throw goes to the catch, and a lenient empty parse yields null HtmlBody/TextBody so BuildPlainBody falls back to the same PreviewText. The row looks normal, opens instantly, and shows a 160-character stub of a real message with no error, for the life of the cache, unless the user force-resyncs the whole folder.

Every piece needed to recover is already built -- DeleteCachedBody, the download-on-missing path, the reader's null branch. None of it is ever reached, because a corrupt body currently reports itself as a successful render.
