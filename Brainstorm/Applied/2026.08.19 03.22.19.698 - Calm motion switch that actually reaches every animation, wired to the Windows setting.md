# Calm motion switch that actually reaches every animation, wired to the Windows setting

Kategori: Accessibility — motion and comfort | Efor: S | Rank: 2

## Ne
Add `Settings.ReduceMotion` (bool, default false) and `Settings.FollowSystemMotion` (bool, default true) to the Appearance block of MainProject/Stores/Settings.cs, next to FollowSystemTheme/UiScalePercent/MessageListDensity. Add a `SystemReducedMotionProbe` Func<bool> in the ThemeConstants layer shaped exactly like the existing `ThemeManager.SystemDarkProbe`, and wire it in MyLovelyMail/MauiProgram.cs:25 beside `ThemeManager.SystemDarkProbe = SystemThemeProbe.PrefersDark`, backed by a new MyLovelyMail/SystemMotionProbe.cs built like SystemThemeProbe.cs (same `#if WINDOWS`, same try/catch + Logger.Warning, false when absent or unreadable). CORRECTION to the proposal: `HKCU\Control Panel\Desktop\WindowMetrics\MinAnimate` is REG_SZ, not REG_DWORD — it reads back as the string "1" on this machine — so SystemThemeProbe's `is int useLight && useLight == 0` pattern must become a string compare (`key?.GetValue("MinAnimate") as string == "0"`); copying the int pattern verbatim would silently return false for every user. Emit the gate as one `AppStyles.BuildCalmMotionLayer()` string (sits next to BuildAuroraStopsLayer) that MainLayoutCss.razor drops in near the existing aurora block: `*, *::before, *::after { animation-duration: 1ms !important; animation-iteration-count: 1 !important; transition-duration: 1ms !important; scroll-behavior: auto !important; }`. `animation-iteration-count: 1` is the load-bearing declaration — it stops the loops rather than speeding them up. Keep the same declarations under a `prefers-reduced-motion: reduce` media query that is always emitted, so the OS preference still works when the app switch is off (do not let the app toggle gate the media block). Expose both toggles in Settings.razor next to the UI-scale field and the density buttons, through the same SetAndSave path the other rows use. Verify with `GET /motion` returning `{ reduceMotion, followSystem, systemReduced, effective, css }` and `POST /motion?reduce=true|false`: the test asserts `css` is empty when motion is normal, contains `animation-iteration-count: 1` when calm, `systemReduced` matches the registry, and a re-read of `GET /status` confirms the setting persisted.

## Neden
Verified in the repo: MainLayoutCss.razor:55 wraps only `body::before` in `prefers-reduced-motion: no-preference`, and it is the sole occurrence of that query in the whole UI. Everything else loops unconditionally — `sync-heartbeat` (SyncHeartCss.razor:46), `sync-sweep` (MailCss.razor:232), `inbox-zero-drift` (MailCss.razor:1155), `mini-unread-pulse` (SettingsCss.razor:204) and both spinners. So the aurora goes calm while the sync heart keeps beating and the hearts keep drifting, which is backwards: the looping elements are the ones that actually trouble a motion-sensitive user. Settings.cs has theme, follow-system-theme, UI scale, density and unread badges under Appearance and nothing at all for motion, so there is no in-app way to stop them. One emitted CSS string covers every animation with no per-keyframe edits, the probe copies a pattern already proven in this repo, and the whole thing is checkable over HTTP — the registry read, the effective gate and the persistence round-trip are all real assertions rather than restatements of the code under test.
