# Version number comes from one source instead of a hand-typed literal

Kategori: release-hygiene | Efor: S | Rank: 1

## Ne
AppConstants.AppVersion is a hand-typed string ("v1.33.0") rendered at the foot
of Settings.razor. Replace it with a value read from the assembly the app is
actually running: set <Version> in MyLovelyMail.csproj (and MainProject.csproj)
as the single source, then have AppConstants.AppVersion return
Assembly.GetExecutingAssembly().GetName().Version (or the
AssemblyInformationalVersionAttribute, which keeps a "v" prefix and any
pre-release suffix intact). Then close the other half of the loop: Release.ps1
already computes the next tag from the highest existing one -- have it write
that number into the csproj <Version> before it publishes, so the tag, the two
zip assets and the string on screen cannot disagree. Verify by publishing a
throwaway bump and checking that GET /settings-version (or the DOM of
/Settings) reports the same number the release tag carries.

## Neden
Three places have to agree today and nothing enforces it: the git tag
Release.ps1 creates, the assets it uploads, and the literal in AppConstants. The
failure is silent in the direction that matters most -- the screen keeps showing
the old number after a release, so the one thing the line exists to answer
("which build am I running") is answered wrongly, and a bug report arrives
against a version that was never installed. Publishing already knows the real
number; the literal is the only step that does not.
