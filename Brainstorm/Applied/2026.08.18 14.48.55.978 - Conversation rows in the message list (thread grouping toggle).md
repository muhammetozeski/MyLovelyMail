# Conversation rows in the message list (thread grouping toggle)

Kategori: threading-ui | Efor: M | Rank: 1

## Ne
Group the open folder's messages into one row per conversation inside the existing Virtualize list. In Mail.razor.cs add a `List<MailThread> FilteredThreads` filled at the end of RefreshLists() via ThreadingService.BuildThreads(FilteredSummaries), active only when the EXISTING `Settings.ConversationView` bool (already defined in Stores/Settings.cs:78 with a per-account InheritedSetting in AccountSettings.cs:33 — currently consumed by nothing; do NOT add a new setting) is on and SearchText is empty (search keeps the flat list so hits stay visible). In Mail.razor, when conversation mode is active, switch the Virtualize to `Items="FilteredThreads" Context="thread"` rendering the existing mail-row markup from thread.Newest, plus a count pill (e.g. "3") after the sender name when thread.Messages.Count > 1, sender text from thread.ParticipantAddresses/names joined with ", ", and mail-row--unread driven by thread.UnreadCount > 0. Row click calls the existing HandleRowClick with thread.Newest so reader, Ctrl+Click selection and keyboard focus keep working (MoveFocus in Mail.razor.Interaction.cs walks FilteredThreads.Select(t => t.Newest) when the mode is on). Add the on/off control as a mail-search-toggle style button ("🧵 Conversations") in the mail-search block of Mail.razor, persisting through SettingsManager.SaveSettings(). Pill styling goes in MailCss.razor. Since ConversationView defaults to true, the mode is live immediately after the change — verify the default folder view through the DebugApi.

## Neden
ThreadingService.BuildThreads and the /threads DebugApi endpoint already exist but no user-visible UI consumes them — verified: the only BuildThreads caller is zTests/DebugApi.cs:219, and Settings.ConversationView plus its AccountSettings override already sit unused, so the model, the grouping service and the setting are all shipped with zero UI payoff. One row per conversation with a count pill is the highest-value return on that sunk work, reuses MailThread's Newest/UnreadCount/ParticipantAddresses aggregates exactly as designed, and the pre-existing setting trims the stated scope below its M estimate.
