# Forward as attachment (the original .eml rides along)

Kategori: compose | Efor: S | Rank: 1

## Ne
Add ComposeService.BuildForwardAsAttachment(account, folderFullName, summary) beside BuildForward. It reads the cached raw MIME with MessageStore.TryLoadFullMessage(account.Id, folderFullName, summary.Uid); when that returns null (body never fetched) it falls back to plain BuildForward and logs a warning rather than handing back a draft with a phantom attachment. On success it writes the bytes into the draft's AttachmentStageFolder as AttachmentService.SafeFileStem(summary.Subject, $"message-{summary.Uid}") + ".eml" via AttachmentService.UniquePath and puts that path on draft.AttachmentPaths. Body is the attribution line only -- QuoteBody(..., styleOverride: QuoteStyle.None) -- so the forwarded copy IS the attachment, not a re-typed transcript. Subject keeps the existing Fwd: rule. SourceFolder/SourceUid stay set, as BuildForward does. In Mail.razor:642 the single Forward SecondaryButton becomes two chips ("Forward" / "Forward as attachment"), the second calling a new StartForwardAsAttachment in Mail.razor.Reader.cs:271 that wraps WithAccountAndFolder exactly like StartForward. No lifecycle code is needed: the compose pane already renders AttachmentPaths chips (Mail.razor:503) and DeleteDraft already deletes the stage folder (ComposeService.cs:98-107). Verify with a new DebugApi case ("GET", "/forward-attach") that builds the draft and returns the staged path, its byte length next to the cached MIME length, and the MIME type MimeKit assigns the part in SendAsync's BodyBuilder loop -- if BodyBuilder.Attachments.AddAsync gives the .eml application/octet-stream instead of message/rfc822, pin it as a MimeKit MessagePart in that loop.

## Neden
BuildForward (ComposeService.cs:196) sets only Subject and a quoted Body; AttachmentPaths stays empty and SendAsync (line 284) builds the outgoing message from that list alone. So forwarding an invoice sends the recipient the words and not the PDF, with nothing on screen saying the file was dropped -- a silent data loss on a top-three reader action, not a missing feature. Attachment-forwarding is also the only way to pass a message on with its headers, DKIM signature and the Received chain MessageAuthService reads still intact, which is exactly what forwarding a suspected phish requires. The pieces are all in place already (TryLoadFullMessage, SafeFileStem, UniquePath, the stage-folder wipe, the chip renderer), and SendGuardService needs no change: the attachment reminder stays quiet because the list is non-empty, and the size ceiling correctly counts the forwarded .eml.
