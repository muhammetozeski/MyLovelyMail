# Zero-hit search rescue chips

Kategori: search | Efor: M | Rank: 1

## Ne
When the list hits its "Nothing matches your search" branch (Mail.razor:174-177), render up to four clickable chips beneath it, each naming a change that brings results back plus its real hit count. New static MainProject/Services/SearchRescueService.cs exposes Suggest(accountId, folderFullName, query, searchAllFolders). It splits the query on spaces and, for each token, re-runs SearchService.BuildMatcher on query-minus-that-token over the same source the page uses — MessageStore.GetSummaries(accountId, folder) for in-folder, SearchService.Search(accountId, q) for the whole account — counting matches. It always also tests the untouched query in all-folders mode, since "right query, wrong folder" is the most common miss. Dead operators get their own chip: SearchService.ParseQuery gains a third returned list of tokens that fell through to the default arm, and a token is dead when it landed there AND its prefix is one of has/is/after/before/on/newer_than/older_than (from:/to:/tag: accept any value, so they are never dead) — no re-encoding of the switch's value guards, so the check cannot drift from the parser. Suggestions come back ordered by hit count, rendered with the existing .mail-search-toggle style (MailCss.razor:258); clicking one sets _searchText (and SearchAllFolders where relevant) and calls RefreshLists, the same paths ToggleSearchToken/ToggleSearchAllFolders already use. Verify off-screen with a new GET /search-rescue?accountId=&folder=&query= case in zTests/DebugApi.cs returning the suggestion list; "is:unred", "from:nobody is:starred" and a term that exists only in Sent exercise each suggestion kind against the real cache.

## Neden
ParseQuery's default arm turns any unrecognized operator into a literal text token, so is:unred, has:attachments and a mistyped date all become searches for that string and return nothing — the query looks correct and the app says only that nothing matched. Every fact needed to explain the miss is already in memory: the matcher is public and takes a raw string, the per-folder summaries are in RAM, and the operator table is one switch. This turns the emptiest screen in the app into the one that hands back a query that works, without touching the search engine's behavior.
