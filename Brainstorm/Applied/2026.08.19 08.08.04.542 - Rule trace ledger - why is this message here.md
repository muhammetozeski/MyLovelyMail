# Rule trace ledger: "why is this message here?"

Kategori: Diagnosability | Efor: M | Rank: 1

## Ne
New `MainProject/Services/Mail/RuleAuditStore.cs` — an append-only JSONL ring buffer at `AppPaths.UserData/rule-audit.jsonl`, written through `AtomicFile`/`JsonDefaults` the way `SyncHealthService` writes sync-health.json, capped at ~2000 entries. Each record: `{ WhenUtc, AccountId, FolderFullName, Uid, MessageId, RuleId, RuleName, Action, Argument }`. Hook it inside `RuleEngine.ApplyActions` — one entry per action actually applied (MarkRead, MarkImportant, Flag, Mute, AddTag, SetNotificationSound, MoveToRemoteFolder, MoveToLocalFolder), plus one entry when `rule.StopProcessing` short-circuits the loop in `ProcessIncoming`, so "why didn't my second rule run" is answerable too. Note `ApplyActions(rule, summary, result)` does NOT currently have the account or folder in scope — `ProcessIncoming(account, folderFullName, newSummaries)` does, so thread both through the call at RuleEngine.cs:48. Key each entry on `MessageId` as well as (folder, uid), because `ImapSyncService.ExecuteRuleMovesAsync` calls `MessageStore.RemoveMessages(account.Id, folder.FullName, ...)` immediately after a successful remote move (ImapSyncService.cs:431), so the source-folder uid no longer exists by the time anyone asks. Both sync paths funnel through the one method (`ImapSyncService.cs:387`, `Pop3Service.cs:65`), so the single hook covers IMAP and POP3 alike. In `Mail.razor` add a chip in the reader header block that already carries the `mail-auth-chip` / `mail-unsubscribe` markup (around Mail.razor:465): `🧭 Marked read by rule "Quiet CI"` / `🧭 Moved here by "Newsletters"`, click navigates to /FilterRules. Verification without a mail server: `GET /rule-audit?accountId=&folder=&uid=` and `POST /rule-audit/probe` in `zTests/DebugApi.cs`, the probe feeding a synthetic `MailMessageSummary` straight to `RuleEngine.ProcessIncoming` exactly the way the existing `POST /mute/incoming-probe` case (DebugApi.cs:396) builds its probe summary; then `GET /dom?selector=.mail-rule-trace` proves the chip rendered.

## Neden
`RuleEngine.ApplyActions` sets `summary.Flags |= MailFlags.Seen`, appends tags and queues moves, and records nothing anywhere. The only trace a rule leaves today is `Log($"Rule move to '{moveGroup.Key}' failed: {ex.Message}", LogLevel.Error)` in `ImapSyncService.ExecuteRuleMovesAsync` — the failure path only. A rule that works perfectly is completely invisible: mail arrives already-read, silently tagged, muted, or simply absent from the Inbox, and there is no way to learn which rule did it or that a rule was involved at all. `RuleEngine.Preview` answers "what would this rule do" before arming it; nothing answers "what did it already do", which is the question asked after the surprise.
