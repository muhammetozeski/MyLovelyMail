# Sender authenticity strip in the reader

Kategori: Trust and sender identity | Efor: M | Rank: 1

## Ne
New `MainProject/Services/Mail/MessageAuthService.cs` cloned from `UnsubscribeService`'s shape: `Inspect(MimeMessage)` is the pure core, `Read(account, folderFullName, summary)` is the thin `MessageStore.TryLoadMimeMessage` + try/catch wrapper returning null when there is nothing to say. Findings are `readonly record struct AuthFinding(string Code, string Text)` with `public const string` codes, mirroring `SendWarning` in `SendGuardService.cs:7` so wording never leaks into checks.

FOUR CORRECTIONS to the proposal as pitched, all required:

1) Read ONLY the topmost `Authentication-Results` header (`message.Headers` in order, first match wins). Everything below it was supplied by the sender and can say whatever an attacker wants. Same for `Received-SPF`.

2) NO green pass chip. A `dkim=pass` from a header anyone can prepend is not evidence, and a reassuring green badge on a forged header launders the phish — strictly worse than showing nothing. The strip renders only when there is something wrong or missing; a clean message shows no strip at all, which also keeps the reader calm.

3) DROP `name-claims-domain` (the ContactIndexService-weighted "FromName ends in a known domain" check). It fires on every legitimate `Amazon.com`, `GitHub`, `Microsoft Account` display name. Keep `name-claims-address`, which is exact and unarguable: FromName contains a literal `@`-address whose domain differs from FromAddress.

4) Suppress the whole strip for local folders (`folderFullName.StartsWith(MessageStore.LocalFolderPrefix)`) and for messages from the account's own address. Drafts, Sent and imported `.eml` were never stamped by a receiving MTA, so `unauthenticated` would fire on all of them and the chip would become wallpaper.

Codes kept: `spf-fail`, `dkim-fail`, `dmarc-fail`, `unauthenticated` (no auth headers at all), `return-path-mismatch`, `reply-to-elsewhere`, `name-claims-address`. Domain comparison is a plain case-insensitive suffix/equality check on the full domain — no registrable-domain / public-suffix guessing, and `mail.github.com` under `github.com` counts as a match.

Rendering: fill an `authFindings` field in `Mail.razor.Reader.cs` on the line next to `unsubscribeTargets = UnsubscribeService.Read(...)` (`Mail.razor.Reader.cs:139`), same lifetime, cleared with the message. Chips go in `Mail.razor` right under the `mail-reader-history` button (`Mail.razor:433-439`), with `.mail-auth-chip` in `MailCss.razor` cloned from `.mail-reader-history` (`MailCss.razor:560`) and colored from `AppColors.TextWarning` / `TextOnWarning` — never a raw hex.

Verification: `POST /auth` in `MainProject/zTests/DebugApi.cs` taking raw MIME on the request body (`MimeMessage.Load(request.InputStream)`, the same `request.InputStream` pattern already at line 265) and returning the codes — every case provable by piping a handcrafted header block at 127.0.0.1:52539 with no mail server; plus `GET /auth?accountId=&folder=&uid=` over a real cached message reusing `RequireAccount`/`RequireSummary`/`ReadFolder`.

## Neden
The reader prints `@open.FromName <@open.FromAddress>` with zero scrutiny (`Mail.razor:429`), and a grep for Authentication-Results, DKIM, SPF, DMARC, Return-Path and Reply-To across the entire codebase returns nothing — the app caches these verdicts on disk in every message and has never once looked at them. The work is header parsing plus chips; no protocol traffic, offline-readable, and provable end to end through the DebugApi with a text file. `reply-to-elsewhere` and `name-claims-address` catch the attack that the Source view can currently only reveal to someone who already suspects it and knows which header to scroll to.
