# Stale-folder rotation: folders you never open still get refreshed

Kategori: sync | Efor: M | Rank: 1

## Ne
Today MainProject/Services/Mail/ImapSyncService.cs SyncAccountAsync (line 156) does exactly two things: SyncFolderListAsync, which already calls folder.StatusAsync(Count|Unread|UidValidity) on EVERY folder (line 212), and SyncOpenedFolderAsync(client.Inbox). Message summaries for every other folder arrive only through MailUiState.SelectFolder -> ImapSyncService.KickFolderSync (MailUiState.cs:72) - verified as the only caller. Add a rotation that rides the connection SyncAccountAsync already has open.

1) MailFolderData (MainProject/DataModels/Mail/MailFolderData.cs) gains DateTime? LastSyncedUtc, set at the end of SyncOpenedFolderAsync. It MUST be carried over in SyncFolderListAsync's SaveFolder exactly the way LastSeenUid/OldestFetchedUid are (ImapSyncService.cs:226-227) - that block rebuilds the record from scratch and the comment above it documents this same trap.
2) In SyncAccountAsync, after the Inbox, pick the N stalest server folders: skip IsLocal, skip the Inbox, prefer folders whose server Count from the STATUS call already differs from the cached TotalCount (free evidence something changed), then order by LastSyncedUtc ascending, take N, and call SyncOpenedFolderAsync for each over the SAME ImapClient.
3) SyncOpenedFolderAsync gets a bool backgroundRefresh parameter, true only for rotation folders. When true it skips BOTH the NotificationService.NotifyNewMessages/PrefetchAttachmentBodiesAsync block (line 368-373) AND the RuleEngine.ProcessIncoming block (line 343-350). The notification half is obvious - mail landing in Sent or Trash must not raise toasts. The rule half matters more: RuleEngine.ProcessIncoming is not folder-scoped, so without this guard a rotation pass would start executing move actions on Sent/Junk/Trash arrivals in the background with nobody watching. Rotation must stay a pure refresh; rules keep running only where they run today.
4) New Setting<int> BackgroundFolderRefreshCount = 2 in MainProject/Stores/Settings.cs with an InheritedSetting twin in AccountSettings.cs, plus a number field in UI/Pages/Settings.razor next to the sync interval at line 130. 0 = off, for anyone who wants Inbox-only traffic.
5) Folder rows in UI/Pages/Mail.razor get a title tooltip with the relative LastSyncedUtc age, so 'this folder is from three weeks ago' is answerable without guessing.

Verification, no clicking: extend GET /folders in MainProject/zTests/DebugApi.cs (line 318, which already returns LastSeenUid/OldestFetchedUid/CachedCount) with LastSyncedUtc, and add POST /sync/folders?accountId=&count=1 that runs one rotation step and returns which folder it picked. Call POST /sync three times and watch a different folder's LastSyncedUtc and CachedCount advance each time while the Inbox advances every time; set the count to 0 and confirm nothing but the Inbox moves.

## Neden
Over a day this is the difference between a mail client and a snapshot. All-folders search is cache-only - SearchService iterates MessageStore.GetFolders then GetSummaries (lines 53-55) - so anything that arrived in a folder you have not clicked is unfindable, while SyncFolderListAsync's StatusAsync keeps that folder's unread badge perfectly current. A badge that says 4 unread over a message list from three weeks ago is the unread-count-vs-contents mismatch in its worst form. It also closes the sibling case: RuleEngine remote moves push mail into folders that then never sync again on their own. The cost is zero extra connections (it reuses the client SyncAccountAsync already opened) and zero extra STATUS calls (SyncFolderListAsync already made them), and N is a user-visible dial for anyone who wants less traffic.
