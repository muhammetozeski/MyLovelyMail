# Free Tab from the message list, and show which control owns the keyboard

Kategori: keyboard-access | Efor: M | Rank: 1

## Ne
Three changes, all verified against the current tree.

(1) Delete `@onkeydown:preventDefault="true"` from the `.mail-rows` div (MainProject/UI/Pages/Mail.razor:228). It cancels every keydown that reaches the handler — including ones bubbling up from the row buttons — so Tab and Shift+Tab are dead the moment focus enters the list. Note that Blazor evaluates `:preventDefault` as a render-time expression, not per event, so it cannot be made key-conditional without lagging a render; remove it outright. Arrow keys will then also scroll the list while the focus ring moves, which is the wanted behavior anyway, and Ctrl+A falling through to the browser's select-all inside a WebView is harmless.

(2) Add real `:focus-visible` rules to MailCss.razor beside the existing `.mail-row--focused` block (line 358), using `AppColors.Accent` and `AppMeasures.Border.Medium` so the DOM ring matches the app-state ring, and replace `.mail-rows:focus { outline: none }` (MailCss.razor:363) with a visible list-edge highlight. Cover `.mail-account`, `.mail-folder`, `.mail-folder-action`, `.mail-search-toggle`, `.mail-row`, `.mail-move-option`, `.mail-attachment-chip`, `.mail-tag-chip`, plus CoreButtonCss.razor and CoreInputCss.razor — the latter sets `outline: none` at line 23 and puts nothing back.

(3) Add `x` to the HandleListKeyDown switch (Mail.razor.Interaction.cs:195) calling `MailUiState.ToggleSelected(focused.Uid)`, and add the row to ShortcutHelpRows. `.mail-row-check` is a `<span>` with `@onclick` (Mail.razor:236), so per-row bulk selection has no keyboard route at all today — only Ctrl+A for select-all, which is itself implemented but undocumented in the cheat sheet.

Verify headlessly through the DebugApi: `GET /dom?selector=:focus` returns the focused element's outerHTML (MainPage.xaml.cs:31 feeds the selector straight to `document.querySelectorAll`, so `:focus` works), `GET /dom?selector=button,input,[tabindex]` enumerates the tab stops in document order, and `GET /dom?selector=.mail-row-check--on` confirms `x` toggled the focused row.

## Neden
A keyboard user who reaches a message row is trapped: the container preventDefaults every keydown, so the sidebar, the search box and the reader are unreachable without a mouse. And the repo contains zero `:focus-visible` rules — grep confirms it — while `outline: none` appears in six places, so nothing tells you which control is listening. The one visible ring, `.mail-row--focused`, tracks `MailUiState.FocusedMessage` rather than DOM focus, so it stays lit while the keyboard is somewhere else entirely.
