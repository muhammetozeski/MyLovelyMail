# Outbox attempt ledger: what failed, how many times, and a hold that stops the silent spinning

Kategori: outbox-visibility | Efor: M | Rank: 1

## Ne
Add OutboxAttemptStore.cs beside RuleAuditStore.cs, copying that file's shape exactly (jsonl under AppPaths.UserData, lazy static cache, AtomicFile.WriteAllText, JsonDefaults.SingleLine, corrupt-line skip). One entry per queued message keyed by AccountId + Uid: AttemptCount, LastAttemptUtc, LastError, HeldUtc. Wire it into the three branches already inside OutboxService.FlushAsync's per-message loop (OutboxService.cs:146-173): the success path after RemoveMessages (line 163) clears the entry; the dropped-MIME path (line 158) also clears it, so entries never outlive their message; the catch (line 168-170) calls Record(account.Id, queued.Uid, ex.Message). The top of the loop skips any uid whose AttemptCount is at or above a ceiling constant (5) until a Try now clears its hold. Surface it in two places only. In the list, when MailUiState.SelectedFolder is { Role: FolderRole.Outbox }, add a status line to the mail-row-preview block (Mail.razor:295) reading "Queued, 3 tries, last: Connection refused" or, once held, "Stopped after 5 tries, last: ...". In the existing undo-bar stack (Mail.razor:386-401), add one bar when any account has held messages -- a single count, not one bar per message -- with a Try now button that clears the holds and calls FlushAsync, since Outbox is a folder the user has no reason to open. Extend GET /outbox (DebugApi.cs:760) with a queued array of { accountId, uid, subject, attempts, lastError, held } and add POST /outbox/hold/clear?accountId&uid. Verify with no external service: point an account's SMTP at a dead local port, which raises SocketException and satisfies ComposeService.IsConnectionFailure (line 310) so the message parks in the Outbox, then drive POST /flush-outbox and read the climbing counter and the hold back from GET /outbox.

## Neden
A permanently misconfigured SMTP endpoint fails completely silently, forever. The user gets exactly one notification, at queue time, from OutboxService.RunSendAsync's QueuedOffline branch (OutboxService.cs:117-122), and it makes a promise the code cannot keep: 'is waiting in Outbox and will be sent automatically'. After that, every sync pass calls FlushAsync (SyncScheduler.cs:105-108), and its catch block does nothing but Log(..., LogLevel.Warning) -- no counter, no ceiling, no retry limit. The Outbox row carries no state at all, so the folder meant to be where you inspect stuck mail looks identical whether a message left thirty seconds ago or has been failing for three days. GET /outbox reports only the undo-window send and the last failure bar, so even the DebugApi cannot see a stuck queue. SyncHealthService already keeps exactly this bookkeeping -- last success, last error, failure streak -- for the receiving side; the sending side has no equivalent.
